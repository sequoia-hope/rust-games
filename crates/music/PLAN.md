# The music engine: plan

Written 2026-10-19 from `docs/music-engine-kickoff.md` (the owner's brief:
clean up, research, upgrade the generator, a listening and learning UI).
This is the plan to agree before the big refactors; the questions for the
owner are at the end.

## Where it stands

`crates/music` (package `mp_music`, 16k lines) is Midnight Playground's
JavaScript Music Lab ported line for line, with the lab as its oracle
(goldens in `tests/golden/`, every random draw in the lab's order).

- **Pipeline.** A genre is a hand-written function `make(seed, dejavu) ->
  Track` (`genres.rs`, 330 to 1180 lines each, 9 genres). A `Track` is the
  old JS song format, string-typed: named chord progressions, drum step
  strings, part pattern strings, and a list of 9 to 11 sections, which
  `compose::expand` cuts into 8-bar blocks (15 to 18 per song). Each block
  plays the core pattern or one of a few mutated variants (the déjà vu
  control). `seq.rs` turns that into note events per 16th; `engine.rs` plays
  them through the instruments (303, Juno-style poly, Moog-style mono, 4-op
  FM, plucked and bowed strings, 808/909/latin/country kits) and the mix
  (channels, pump, delay, FDN reverb, glue, tape, limiter).
- **Why it sounds weaker than human-made tracks** (evidence in the survey):
  - Arrangement is whole-song blocks: a part is in a section or not, and
    every pattern restarts at each 8-bar block, so nothing carries across a
    boundary and no instrument has its own timeline.
  - Every song of a genre has the same form; variation is one round of
    random mutations of the core, and most blocks replay the core.
  - Harmony is 4-bar loops of one chord per bar, 1 to 3 per song, nothing
    borrowed but the dominant; melody is one 1–2 bar motif per song plus
    its answer a third up.
  - Flat dynamics (three drum velocities, ±6 % humanise), mono delay send,
    one reverb, fixed fills, a global pump depth.
  - Genres are code, not data, so no research can be plugged in as
    parameters.
- **Consumers.**
  - Midnight Playground: `mp_audio` (the native radio processor and the web
    worklet shim, `mp_music.wasm`), `mp_game` (station UI, store, menu),
    `tools/radio*`, `tools/serve.py` and two e2e tests.
  - Snowboarding: `sb_game` through **`sb_music`, a fork** that differs only
    in its station table (one station), because the station table is
    compiled into the worklet wasm. Its xtask hand-copies the worklet build.
- **Game-specific code inside the shared crate:** `radio::STATIONS` (five
  Midnight Playground stations and DJs), `level_station` (its level names),
  the `mpm_` export prefix, `favourites.json`, and comments citing the
  game's DECISIONS and files.
- **Broken today, found by the survey:** the Radio page and `serve.py` read
  and write `crates/mp_music/favourites.json`, which moved; the lab's table
  generators write to the old `crates/mp_music/src/` paths; the lab's tests
  (`npm run test:lab`) ran only in Midnight Playground's own CI, which no
  longer runs.

## Decisions this plan proposes

1. **Rust leads from now; the lab runs on Rust.** Porting every change
   through JavaScript first doubles the work and pins the draw order. The
   lab's JavaScript *engine* (`tools/music-lab/{dsp,instruments,seq,
   compose,gen,engine}.js`) is frozen; the lab's *UI* stays and is pointed
   at the Rust engine: it moves to `apps/music-lab/`, and its worklet
   becomes the Rust wasm, taking the same messages it takes today (track,
   play, stop, patch, kit, audition, note on and off, hit, energy, mix,
   mute, solo). Genres are generated by Rust too, so the lab always plays
   exactly what the games play. The lab's A/B against Midnight
   Playground's old JS songs (`Music.js`, `tracks.js`) stays in the frozen
   copy. The current generator stays, byte for byte, as **`classic`** (its
   goldens keep passing: same seed, same song, so the games sound the same
   until the owner switches a station); the new generator is new code beside
   it with its own Rust-recorded goldens.
2. **Stations are data the game supplies**, not a compiled table. One
   worklet wasm serves every game: the page passes its station table at
   start-up (a new `…_stations(ptr, len)` export, JSON), natively a game
   passes `&[Station]` to `Player::new`. Snowboarding's `sb_music` fork is
   deleted; both games build the worklet through `pk_xtask`'s `SideWasm`.
3. **A clean public API in layers**, everything else `pub(crate)`:
   - `sound`: DSP blocks, instruments, kits, patches (the renderer's parts);
   - `score`: the new song description (below), serialisable to JSON for the
     player and the viewer;
   - `gen`: genre profiles and the generator, `generate(&GenreProfile,
     &Settings, seed) -> Song`;
   - `render`: `Renderer` (today's `Engine`), plays a `Song` (or a classic
     `Track`) to samples, with energy and solo/mute;
   - `radio`: the wall-clock scheduler, `Station`, `cue`, `Tuner`, `Player`;
   - `worklet`: the C ABI (feature-gated, unchanged exports kept as aliases
     until both shims move).
   Every breaking change goes in `CHANGELOG.md` with its migration.
4. **One package rename,** to `music` (the owner's answer 1), done once in
   Phase 1 with the other breaking changes, so consumers migrate once.

## Phase 1: clean up (no change in sound)

1. Fix what's broken: the favourites path (`serve.py`, `tools/radio*`,
   e2e), the lab's generator output paths, stale comment paths.
2. Move game-specific content out: Midnight Playground's stations and
   `level_station` into `mp_audio` (or a small `mp_radio` data module),
   Snowboarding's into `sb_radio`. The crate's docs stop citing one game's
   DECISIONS; the ones that matter are restated in the crate's own
   `DECISIONS.md`.
3. Stations at start-up (decision 2): `Player::new(rate, seed, stations)`,
   the worklet export, both shims and the Radio page pass their table.
   Delete `sb_music`; Snowboarding uses `crates/music`.
4. The layered API (decision 3) and the rename; JS-emulation helpers and
   `json` become private; the classic generator moves under `gen::classic`.
5. **Standalone use:**
   - a native CLI example, `render --genre house --seed 7 --out song.wav`,
     so any song can be rendered and A/B'd without a game;
   - **the lab on Rust** (decision 1): `apps/music-lab/`, the lab's UI over
     the Rust worklet wasm (a `lab` C ABI beside the radio's: generate a
     genre's track, set track, patch, kit, mix, play, notes and hits),
     with its own `serve.sh` (registered with `proj`), `pages.sh` and a
     `site/games.toml` entry. Phase 3 grows it (the new generator's
     settings, the layer viewer) and Phase 4's player is its listening
     page.
6. **Gate:** the classic goldens pass unchanged, both games build and pass,
   the e2e radio tests pass, and a station sounds the same in both games
   (rendered and compared).

## Phase 2: research (parallel agents, into `research/`)

Each agent writes one file with citations (papers, books, interviews,
production tutorials from known producers, with links), and a closing
section of **rules and parameters** in a fixed format, so Phase 3 can turn
them into profiles directly.

| File | Scope |
|---|---|
| `research/genres/house.md` | Chicago, deep, French (filter house), plus garage/UKG |
| `research/genres/techno.md` | Detroit, Berlin, minimal, acid |
| `research/genres/dnb.md` | jungle, drum and bass (liquid, rollers, neuro), breakbeat |
| `research/genres/trance.md` | trance (Goa/psy, uplifting, progressive), eurobeat |
| `research/genres/synthwave.md` | synthwave/outrun, electro, Italo disco |
| `research/genres/ambient.md` | ambient, downtempo, chillout (and whatever else turns up) |
| `research/arrangement.md` | phrase-based layering, DJ intros and outros, builds, breakdowns, drops, risers, fills, by genre |
| `research/cognition.md` | harmony corpora (de Clercq & Temperley, Hooktheory), expectation (Huron, IDyOM), Cheung et al. 2019, Mauch et al. 2015, and work on EDM specifically (e.g. drops and tension, loop-based form) |
| `research/sound-design.md` | the signature machines and patches per genre, mapped to what `sound` can make and what it lacks |

Then one pass of my own: `research/RULES.md`, the distilled, implementable
rules per genre (tempo, drum grammar, bass grammar, harmony palette with
transition weights, sound presets, arrangement templates, surprise
targets), each rule linked to its source. Phase 2 can run while Phase 1's
refactor does, since they touch different files.

## Phase 3: the new generator

- **Score model: per-instrument timelines.** A `Song` has a tempo, key,
  meter and phrase length, section *labels* (for the viewer and DJ talk,
  not as the unit of playback), and a list of **layers**: each layer is a
  role (kick, hats, perc, bass, chords, pad, arp, lead, fx…), an
  instrument patch, and its **clips**: start bar, length, pattern, variation
  and automation. Patterns are indexed by bar within the clip, so a phrase
  carries across a section seam. The renderer plays layers, not sections.
- **Arrangement planner.** From the genre's arrangement templates and an
  energy curve, decide per layer when it enters, drops out, varies and
  returns, always on 8/16/32-bar boundaries, with interactions as rules
  (kick alone → hats → bass → pads; kick and bass out in the breakdown;
  riser and snare build into the drop; a filter opening over 16 bars), and
  with DJ-mixable intros and outros where the genre has them.
- **Genre profiles as data** (Rust constants built from `research/RULES.md`,
  each value commented with its source): tempo, swing, drum grammar
  (per-lane probabilistic templates and fills), bass grammar, harmony
  palette (progressions and chord-transition weights, modes, borrowed
  chords), sound presets, arrangement templates, surprise targets.
- **Surprise-aware generation.** A small variable-order model per genre
  (IDyOM-style, over chords, melody intervals and drum onsets), trained on
  the profile's own grammar plus the published corpus statistics. For each
  phrase, generate N candidates, score their information content and
  entropy, and keep one in the genre's target band: predictable enough to
  groove, surprising enough to hold attention (Cheung et al.: pleasure peaks
  at low uncertainty with high surprise, or high uncertainty with low
  surprise). Repetition and return are scored too, so the hook comes back.
- **RNG inside structure:** the RNG picks among the options a rule allows,
  never replaces the rule. Each decision draws from its own forked stream,
  so changing one layer's choice doesn't reshuffle the whole song.
- **Gate:** per genre, a set of rendered songs the owner listens to and
  rates against the classic ones; a station switches to the new generator
  only when the owner says so.

## Phase 4: the player (listening and learning)

- A page of the lab (`apps/music-lab/`, plain HTML/JS over the Rust
  wasm, no game engine to load): the lab is the workbench (knobs, patches,
  solo and mute), the player is for listening. On the public site at
  `/rust-games/music-lab/` (`pages.sh`, `site/games.toml`); locally through
  a registered `proj` server.
- **Generate:** pick a genre and settings (tempo, energy, sub-style,
  surprise), seed, play, regenerate.
- **Playlist builder:** add, reorder, remove, keep generating; a song is
  its (generator version, genre, settings, seed), so a playlist is a small
  JSON file: saved in the browser and exported and imported as a file.
  Export the album as WAV files (rendered offline in the page).
- **Notes:** per genre and per track, short research-backed notes (why it
  sounds like this, where the sounds came from, the history) with links,
  generated from `research/` at build time; per track, the choices the
  generator made and the rule behind each.
- **Layer viewer:** one row per layer over the song's bars, clips drawn as
  they enter, vary and leave, section labels above, a playhead.

## Order and gates

1. Phase 1 and Phase 2 together (refactor in one branch, research in
   another); I check in after Phase 1's gate and with `research/RULES.md`.
2. Phase 3, one genre end to end first (house), with the viewer's data
   format, so the owner can hear and see the new model early.
3. Phase 4's player as soon as there's a new song to play; then the other
   genres.
